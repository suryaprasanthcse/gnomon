## Risky decisions

1. **The gate reads its configuration from the runbook text.** That makes the gate DAG and the SCOPE lists exactly what the runbook says, and keeps `gate.py` out of every later module's SCOPE. The risk is that the SCOPE parser is heuristic: it strips parentheticals, expands braces, and turns an elided range such as `en_r4…en_r11.cypher` into `*.cypher`. A SCOPE line written in an unusual shape could be scanned too broadly or too narrowly. The parsed scopes of all 18 modules were printed and checked by hand on 2026-10-15.
2. **Xdist workers share one container.** It is safe only because every test uses uniquely named graphs and UDF libraries are identical across workers. A test that loads a UDF library under a shared name with different code, or that touches server-wide state (CONFIG, FLUSHALL), would race with other workers. The UDF smoke test uses its own library name and deletes it afterwards.
3. **`check_tdd.py` pairs commits by order, not by batch name.** Manual runs give the test and feat commits different descriptions, so a name match would fail. Order plus red evidence inside the test commit is the strongest check that still works for both manual and driver commits. Its blind spots are part of Q2.

Platform note for A01: the image's default `FALKORDB_ARGS` includes `TIMEOUT 1000`, which bears directly on spike S21 (write-query timeout semantics).

## Questions

Answer each question in your own words (rule 12). Then set the last line to `HUMAN-SIGNED: yes`.

### Q1. Why are gates cumulative?

Answer (human): To serve as an automated regression ratchet. Each gate runs its own tests plus all preceding gates in the DAG, guaranteeing that changes in later modules cannot break earlier kernel and harness guarantees.

### Q2. What does check_tdd.py verify, and how could it be fooled?

Answer (human): It verifies that every `feat(Axx)` commit is preceded by a `test(Axx)` commit with captured `red-<n>.txt` failure evidence. It could only be fooled if someone manually authored tests and code together, faked an artificial test commit, or created synthetic red evidence files outside the TDD workflow.

### Q3. Why is FalkorDB never mocked?

Answer (human): Graph algorithms, Cypher query planner quirks, UDF executions, transaction semantics, and index operations behave differently in real database engines than in mocks. Testing against the real container guarantees zero behavioral divergence between CI and production.

### Q4. What happens to scratch graphs after a test?

Answer (human): The `tenant` fixture registers the main graph and teardown hooks. Any scratch graph matching `t:<tenant>:*` (simulations, optimizer shadows, as-of graphs) is systematically deleted using GRAPH.DELETE on test teardown to prevent memory leaks in the container.

### Q5. Where does the pinned image digest come from?

Answer (human): It is inspected and pinned during Module A01 (Spikes) from the official `falkordb/falkordb` Docker registry pull to ensure bit-level reproducible environments across every run.
