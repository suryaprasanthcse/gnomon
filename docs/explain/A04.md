## Risky decisions

1. **The I7 guard is stricter than §9.3 (D-15).** The spec's assert guards only count open-ended versions. After `end` leaves `[vf, e)` current, an assert with `vf < e` would overlap it. Every assert shape now also refuses a current closed version whose `vt > $p.vf`, for the same subject (functional) or pair (set), and `cardinality_ok` names it. The property test is what would have caught the gap.
2. **Guard probes recompute `now`.** Probes run after the apply has failed, so they have no `now`. `<NOW>` rebuilds it the way the tick does: `max(Head.pt, timestamp())` live, `$rec_pt` otherwise. The probes are diagnostics only, so a race between apply and diagnosis yields INDETERMINATE, not a wrong write. The probes are hand-written, one per guard group in spec order; A05's parser is meant to generate them mechanically.
3. **M3 trusts `def` to match `def_json`.** M3 recomputes `Kernel.sha256(def_json)` in-query and checks the version and the sha's novelty. The stored `Rule` fields, though, come from `$p.def`, which nothing in-query ties to `def_json`. K3 (A07) re-derives the sha offline from the stored fields, and the kernel service builds both from one `RuleDef` (`register_rule_params`). Other A04 decisions: D-12, D-13, D-14 (three A03 assertions now derive from the registry). One fix after the gate: callers are sorted at load (`0c909db`), because the first multi-caller rules showed `RuleDef.caller` kept YAML order while Rule nodes store it sorted.
