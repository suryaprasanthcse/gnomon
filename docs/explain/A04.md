## Risky decisions

1. **The I7 guard is stricter than §9.3 (D-15).** The spec's assert guards only count open-ended versions. After `end` leaves `[vf, e)` current, an assert with `vf < e` would overlap it. Every assert shape now also refuses a current closed version whose `vt > $p.vf`, for the same subject (functional) or pair (set), and `cardinality_ok` names it. The property test is what would have caught the gap.
2. **Guard probes recompute `now`.** Probes run after the apply has failed, so they have no `now`. `<NOW>` rebuilds it the way the tick does: `max(Head.pt, timestamp())` live, `$rec_pt` otherwise. The probes are diagnostics only, so a race between apply and diagnosis yields INDETERMINATE, not a wrong write. The probes are hand-written, one per guard group in spec order; A05's parser is meant to generate them mechanically.
3. **M3 trusts `def` to match `def_json`.** M3 recomputes `Kernel.sha256(def_json)` in-query and checks the version and the sha's novelty. The stored `Rule` fields, though, come from `$p.def`, which nothing in-query ties to `def_json`. K3 (A07) re-derives the sha offline from the stored fields, and the kernel service builds both from one `RuleDef` (`register_rule_params`). Other A04 decisions: D-12, D-13, D-14 (three A03 assertions now derive from the registry). One fix after the gate: callers are sorted at load (`0c909db`), because the first multi-caller rules showed `RuleDef.caller` kept YAML order while Rule nodes store it sorted.

### Q1. Draw the versions after assert → supersede → end on one service.

Answer (human): Let rewrite 1 (seq S1, pt T1) assert Team A; rewrite 2 (seq S2, pt T2) supersede with Team B; rewrite 3 (seq S3, pt T3) end at vt_end = T3:
   - Version 1 (asserted at S1, closed at S2): (s)-[:OWNED_BY {fid: 'p1#0', vf: T1, vt: INF, ts: S1, te: S2, tf: T1, tt: T2}]->(TeamA)
   - Version 2 (copy created at S2, current: te = INF, valid [T1, T2)): (s)-[:OWNED_BY {fid: 'p2#e', vf: T1, vt: T2, ts: S2, te: INF, tf: T2, tt: INF}]->(TeamA)
   - Version 3 (superseded current created at S2, closed at S3): (s)-[:OWNED_BY {fid: 'p2#0', vf: T2, vt: INF, ts: S2, te: S3, tf: T2, tt: T3}]->(TeamB)
   - Version 4 (ended current created at S3): (s)-[:OWNED_BY {fid: 'p3#0', vf: T2, vt: T3, ts: S3, te: INF, tf: T3, tt: INF}]->(TeamB)
   At the end: Version 2 is the current belief that Team A owned the service during [T1, T2); Version 4 reflects closed current belief of Team B up to T3; zero live projection edges remain.

### Q2. Why can't projections hold future-dated facts?

Answer (human): Projections (`DEP_NOW`, `OWNER_NOW`, `CONSUMES_NOW`) mirror current reality without valid-time attributes for graph algorithms. If future-dated facts (`vf > now`) were projected, algorithms would traverse edges that have not yet occurred in the real world, corrupting BFS, PageRank, and blast radius computations. Restricting `vf <= now` ensures projections stay strictly synchronous with transaction execution.

### Q3. Why does supersede need $p.old_o?

Answer (human): Functional facts require exactly one current version per subject. To prevent blind overwrites and concurrent conflicting updates, $p.old_o acts as an optimistic concurrency guard ensuring the client explicitly confirms the entity being replaced (`old_o.uid = $p.old_o`). If a concurrent rewrite moved the relationship to another target in the interim, the guard fails cleanly.

### Q4. How does M3 verify its own input?

Answer (human): M3 evaluates `Kernel.sha256($p.def_json) = $p.sha` inside the query guard prior to any write. It checks that `def.name <> 'Genesis'`, verifies that `version = max(existing) + 1`, and deactivates any previous active version atomically. The sha check covers `def_json` only: the stored Rule fields come from `$p.def`, which nothing in the query ties to `def_json`; audit K3 re-derives the sha offline from the stored fields.

### Q5. What would break in algorithms without projections?

Answer (human): FalkorDB graph algorithms (`algo.pageRank`, `algo.betweenness`, `algo.bfs`, `algo.SPpaths`) filter paths by relationship label/type, not by edge property expressions (`WHERE f.te = INF AND f.vf <= now < f.vt`). Without projection edges, algorithms would traverse all historical and retracted fact versions as active edges, producing incorrect shortest paths, broken component partitions, and bloated blast radius calculations.
