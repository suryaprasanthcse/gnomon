## Risky decisions

1. **Verdicts are tied to FACTS.md, not to the spec.** A spike passes when the image matches the *recorded* fact, even if that fact is a FAIL. That honours "encode the observation" and catches image drift, but a wrong verdict, written in good faith, would stay green. The red run's "observed PASS/FAIL" lines are the audit trail for each verdict.
2. **Timing and memory spikes use loose budgets on a private container.** The verdicts for S5 (copy < 1 s), S10 (growth ≤ 2× linear) and S13 (residue ≤ 10%) are deliberately loose so a busy laptop cannot flip them. The cost is that they would not catch a 3× slowdown. The measured numbers are in FACTS.md and in the green evidence.
3. **S8 is recorded as FAIL because nothing was checked.** No Cloud endpoint exists, so "unverified" is treated as FAIL and the Docker Compose fallback (D-3) is the design. The test can probe Cloud later through `GNOMON_FALKORDB_CLOUD_URL`.

Facts later modules must respect: a map, or a list holding null, cannot be a property (S1). Keep `TIMEOUT_DEFAULT` at 0 (S21). Never `LOAD REPLACE` a library under traffic (S22). Results cap at 10,000 rows (`RESULTSET_SIZE`). Drop relationship indexes with the FOR-pattern form (F3, D-6).

### Q1. Which spikes failed, and what does each chosen fallback cost?

Answer (human): 
- S8 (Cloud UDF unverified): Fallback is local Docker Compose deployment for live runs. Cost is managing container infrastructure rather than using managed cloud.
- S14 (MEMORY USAGE doesn't report graph key size): Fallback drops the raw byte memory term in the cost model in favor of an index-count budget constraint. Cost is slightly coarser memory tracking in T-C.
- S17 (algo.bfs only traverses outgoing edges): Fallback is running BFS in both directions or adding reciprocal edges. Cost is a minor constant factor in traversal overhead.
- F3 (relationship index drop syntax): Fallback handles syntax variant per client version. Cost is minor DDL adapter logic.

### Q2. What does S4 protect?

Answer (human): Atomic rollback: it guarantees that an error or thrown UDF exception mid-query leaves no partial or dirty writes in the graph. This ensures state transitions remain strictly all-or-nothing.

### Q3. Does F1 change the need for the torn-copy check in §15.2?

Answer (human): No. While F1 confirms FalkorDB GRAPH.COPY is snapshot-isolated, the VERIFY-BASE check in §15.2 is retained as defense in depth against race conditions or incomplete branch creation under high concurrency.

### Q4. Which spike blocks the most later modules if wrong?

Answer (human): S1 (UDF execution in write queries) and S3 (write serialization). If S1 had failed, the kernel would have required a client-side mutex architecture and parameter pre-computation rather than executing atomic composer queries.

### Q5. What did the S1 result do to the kernel design?

Answer (human): Confirming S1 enables pure in-query tick, chain, and digest computation inside P0/Q0 segments, keeping the composer completely stateless and reliant on database-level ACID execution.
