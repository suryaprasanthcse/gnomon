## Questions

Answer each question in your own words (rule 12). Then set the last line to `HUMAN-SIGNED: yes`.

### Q1. Prove F3 in your own words.

Answer: `Kernel.recv` takes l = max(h.pt, m_pt, wall) and returns (l, c). If l equals both pt and m_pt, c = max(lc, m_lc) + 1, which is above m_lc. If l equals pt only, then pt is above m_pt, so the result is already greater. If l equals m_pt only, c = m_lc + 1. If the wall clock is the largest, l is above m_pt. So in every case (r_pt, r_lc) is strictly greater than (s_pt, s_lc). T2 replaces the ordinary tick for receive rules, so the receipt rewrite carries that value, and K9d checks it from the data. In replay mode the recorded clock is required to be after Head, and the relay records max(Head.pt, s_pt) + 1.

### Q2. Why consume unroutable messages instead of rejecting them?

Answer: A channel is FIFO with no gaps: P2 only accepts `chan_seq = next_seq`. A rejected message never advances `next_seq`, so every later message from that sender would be OUT_OF_ORDER forever. Consuming it as `unroutable` (or `superseded`, `noop`) records that it arrived, advances the channel in the same rewrite, and keeps K9b gapless.

### Q3. What happens when a sender's clock runs ahead?

Answer: In live mode P2 requires `s_pt <= timestamp() + MAX_SKEW_MS` (60 s). Beyond that nothing is written and the outcome is SKEW_QUARANTINED. The relay quarantines that channel, records an alert for operators and stops; the message stays queued and other channels keep flowing. P3 does the same for an ack with `r_pt` ahead. The receiver's own clock is never dragged past wall + 60 s (F5). The sender's HLC does not go back, so all its later messages are quarantined too until the wall clock catches up.

### Q4. Why does the relay keep no durable state?

Answer: Everything it needs is in the logs: `XMsg.state` in the sender says what is still queued, `Channel.next_seq` in the receiver says where to resume. A retry is safe because the receipt has pid `rx:<id>` and the ack `ack:<id>`, so a repeat is DUPLICATE, checked before order. A crash at any point is replaced by a fresh relay that finds the same position. Its only memory is the quarantine set; losing it just means the same refusal happens again.

### Q5. How does `gk why` cross graphs?

Answer: It finds the rewrite that last wrote the entity, follows its CAUSED_BY chain in that graph, and when a rewrite's rule is a ReceiveMessage the pid `rx:<id>` names an XMsg whose `origin_tenant` and `origin_rw` identify the sending rewrite in the other graph. It continues with that graph's chain. Edges cannot cross graphs, so the join is done in the client (`fedlog.why`), with a visited set and a hop limit.
