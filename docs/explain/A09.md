## Risky decisions

1. **The model in the committed recording is a deterministic policy, not an LLM (D-38).** The loop, the prompt format, the id firewall and the replay-by-prompt-hash are real, but the responses come from a rule-based stand-in per role. A real model would be recorded with `RecordingLLM` the same way. The recording says this in its meta, and the explain-back should say it too.
2. **I corrected three of my own tests after the RED commit (D-39).** Two used a stale `ir` clock after the ops loops had moved Head.pt, so the kernel refused them with HLC_REGRESSION; the P5 replay test compared a chain hash with a state hash and now checks both, which is stronger. Approved by the human at the G4b checkpoint, with D-37, D-38 and D-40.
3. **A08 changed under A09 (D-40).** OpenIncident now opens two tasks (investigate, communicate), because comms learns its incident from a task it holds, through the same tools as every agent. The agent policies also read the incident's live facts so the investigator does not propose a second cause; EN-R10 still lists older deploys from the window.

## Questions

Answer each question in your own words (rule 12). Then set the last line to `HUMAN-SIGNED: yes`.

### Q1. Narrate P2 in two sentences for a judge.

Answer: P2 is the hallucination and staleness firewall. An agent that names an id no cited read showed (team:hallucinated) is rejected by id provenance as SCHEMA_REJECTED before anything reaches the kernel, and when an operator retracts the ownership fact at seq N+1, Comms' proposal built on its seq-N read is REJECTED_STALE with the stale key (OWNED_BY:svc:a:*) and the retracting rewrite named, so the model can neither invent memory nor act on a fact that has changed.

### Q2. Why are receipts Observe rewrites?

Answer: A receipt changes the outbox row (pending to delivered, to pending with attempts + 1, or to dead), so it must be a rewrite: only a rewrite is applied atomically with a deterministic source id (rcpt:<pid>:<attempts>), chained into the hash log, replayed by K4 and audited. Making it an Observe rewrite also means the world's delivery outcome enters the log the same way an alert or a health reading does, and a duplicate receipt is refused by the new_event guard instead of being applied twice.

### Q3. What makes the triple run deterministic, given LLMs?

Answer: Every input is fixed or recorded: the world comes from a seed, the clock is the injected simulated clock, ids and pids are derived (exp:<task>:<from_seq>, rcpt:<pid>:<attempts>, <agent>:<step>), and every model response is replayed from a store keyed by the prompt hash, failing on a miss. The prompt is canonical JSON of what the agent read, so identical state gives an identical prompt and an identical recorded answer, and the replayed runs end with the same state hash. In the committed recording the responses come from a deterministic PolicyLLM stand-in, not a real model.

### Q4. Where is the hidden ground truth, and why can it disagree with the graph?

Answer: It lives in the infrastructure simulator (gnomon/sim/infra.py), outside the graph: it knows which deploy is bad and computes true health from the running deploy, its hard dependencies and the service mode. The graph only knows what was observed (Observe.health events with seeded latency) and what was asserted: the bad deploy's expected_health is ok in the graph while the simulator has the service down, until the investigation records the root cause and the rollback shows up as health events.

### Q5. What would you show first in a 60-second demo?

Answer: I would show P2 first: an invented id is refused before it reaches the kernel, and a proposal built on a read that a retraction has since changed is REJECTED_STALE with the key and the rewrite that changed it named. That is the claim a judge cares about, that models cannot corrupt memory or act on stale facts, and it takes seconds. Then P3, the killed agent whose lease expires and whose replayed proposal is a DUPLICATE, and finish with the replay hash and K1 naming an edited rewrite.
