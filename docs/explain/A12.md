## Built

The self-optimizing engine: it watches which reads agents actually run, tries candidate indexes on disposable copies, scores the measured change in integer microseconds, and records the winner as a decided, logged schema change. It never runs DDL on live; the reconciler does, after the log says so, and audit K8 checks the server against the log.

## Questions

Answer each question in your own words (rule 12). Then set the last line to `HUMAN-SIGNED: yes`.

### Q1. Why is the reconciler the only process allowed to run DDL on live?

Answer: DDL cannot share a query with writes, so it can never be a rewrite and replay can never reproduce it. The system therefore splits it: the optimizer only decides (M1, a logged intent, with a proof), and one stateless process, `Reconciler`, runs the statement and attests the outcome with M2. M1 is callable only by the `optimizer` role and M2 only by the `reconciler` role; the optimizer's trials write scratch copies named `<live>:opt:<run>:*` and nothing else. The reconciler re-derives everything from IndexEntry and `db.indexes()` on each tick, so a crash between DDL and M2 only costs a re-settle, and a retried M2 is DUPLICATE (`settle:<key>:<requested_seq>`).

### Q2. What is reproducible in an index decision, and what is only attested?

Answer: Reproducible from the log: the plans (K7 rebuilds the base at `read_seq`, restores the optimizer indexes, applies each candidate's DDL on a copy and compares `plan_before` and `plan_after` exactly), the medians, MADs, benefit, harm, `score_num` and the winner (recomputed from the raw samples in the envelope), and the workload and sample digests. Only attested: the raw microsecond samples themselves, the build time, the synthesized write timings, and the physical outcome in M2 (`ddl_ms`, the fact that the index became operational). K8 later audits that physical outcome against the log.

### Q3. Explain the cooldown's purpose.

Answer: It stops flapping. M1 refuses to re-create a key that settled as retired or failed, or to drop an operational optimizer index, until `settled_pt + OPT_COOLDOWN_MS` has passed, so measurement noise cannot make the optimizer create and drop the same index in a loop. The engine has its own COOLDOWN state after each run (`cooldown_until`), so runs are spaced by the same constant, and the in-flight guard allows only one change at a time.

### Q4. How does K8 catch an out-of-band index?

Answer: K8 reads `CALL db.indexes()` and `CALL db.constraints()` and compares them in both directions with the logged IndexEntry and ConstraintEntry rows. An operational index nobody logged is `index_unlogged` (MU25 creates one); a logged operational index the server does not have is `index_missing_physical` (MU24 drops one); constraints are checked the same way. Entries still `requested` or `retiring` and indexes still building are skipped (D-61). The reconciler also reports both cases as alerts, but never writes.

### Q5. What does the optimizer refuse to touch?

Answer: It never runs DDL on live. It never proposes dropping a genesis-origin index or an index that supports a constraint (the candidate filter's `off_limits`), creates nothing beyond `OPT_INDEX_BUDGET` operational optimizer indexes, nothing that already exists or is requested, and no key still cooling down; M1 repeats the budget, cooldown, origin and single-in-flight checks as guards. It makes no candidate from predicates it cannot index (a function of a property, a NOT, an OR across different properties), and it discards a create whose EXPLAIN does not change to an index scan.
