## Risky decisions

1. **A second platform panic, fixed in the transport (S24, D-20).** Under the gate's 4-worker load one run's server aborted in `slow_log.rs`. A slow write is truncated at byte 2048 for the slow log, and if that byte is inside a multi-byte character the process dies. Our segment and body comments use `─`, `·`, `§`. I reproduced it deterministically and found parameters are not affected. I then had the service send composed queries with comments stripped, which is ASCII and means the same. It edits `service.py`, outside SCOPE, so it was applied as proposed during the autonomous run and approved by the human at this checkpoint. The rejected alternative was making every source ASCII, which changes every sha.
2. **The parser's semantics are my reading of §5.5 and §7.4–§7.6 (D-16).** In particular:
   - `guard_reads` are all reads before the first write: MATCH maps, WHERE and WITH, not only WHERE.
   - A `…:state` key covers its type's non-identity properties, so reading only `Task.id` does not guard `Task.state`. That is what names `Task.state` in ClaimTask_v0's L1 message.
   - A creation counts as guarded by an identity check of something created with it: the `uid` absence check of RegisterEntity, or a new agent's `HAS_SKILL` edges.
   - L3 treats `id` on Entity kinds and any relationship `fid` as unique (§3.3).
   - Genesis (PG) is exempt from L1 and counts as guarded in the matrix, because its guards live in the prelude and it runs once.

   A different reading would move pairs between `guarded` and `unguarded`. The rules are in the module docstrings.
3. **Declared footprints are generated, then pinned (D-17).** Each rule's `reads`/`writes` were regenerated from the parser, and the test requires an exact match. That turns L4 into a drift detector rather than an independent check: a parser bug would be copied into the declarations. Dynamic verification is the independent check. It applies every registered rule in sim mode, Genesis included, and diffs the real graph, and none of its examples found a write outside the declarations. Other A05 decisions: D-18 (service delegates keys and lints M3) and D-19 (A04's M3 tests use RegisterEntity.Team-derived rules).

## Questions

### Q1. What is the difference between a guarded and an unguarded conflict?

Answer (human): A guarded conflict occurs when two rules have overlapping footprints (W_A ∩ (R_B ∪ W_B) ∪ W_B ∩ R_A ≠ ∅), but every conflicting property or relationship is checked in antecedent WHERE guards prior to any write or protected by OCC KeyVersion checks. An unguarded conflict modifies state without verifying the current value in a guard, risking lost updates or race conditions, and is refused at registration by Lint L1.

### Q2. Why must key templates depend only on params?

Answer (human): Write keys must be pure functions of the rule definition and proposal parameters ($p). If key templates depended on runtime graph state, keys could not be pre-instantiated, verified by static linting (Lint L5), tracked for OCC in KeyVersion, or independently validated and recomputed during audit replay without executing queries.

### Q3. What does dynamic verification catch that the parser cannot?

Answer (human): The static parser analyzes syntactic AST patterns, but cannot determine runtime graph traversal paths, conditional FOREACH-CASE execution outcomes, or hidden property mutations across complex matches. Dynamic verification executes proposals on disposable scratch copies (t:<tenant>:replay:fpv-<n>) and diffs the canonical state before and after, guaranteeing that actual writes strictly equal or are a subset of declared writes.

### Q4. Explain ClaimTask_v0's race.

Answer (human): ClaimTask_v0 omitted the guard checking for existing unclosed HOLDS edges, and it does not check Task.state either. If two agents concurrently claim the same task, neither verifies the task is still open or unleased, so both write a HOLDS lease and both set Task.state = 'claimed', violating Invariant I6 (at most one unclosed lease per task). Lint L1 catches this because HOLDS and Task.state are written under instance keys without a guard reading what those keys cover (`L1 unguarded write: HOLDS (HOLDS:*:{p.task}), Task.state (Task:{p.task}:state)`).

### Q5. Which matrix entry surprised you?

Answer (human): R2.OWNED_BY × R9 (PostUpdate), from the §7.6 table in the spec (R9 is registered in A06, so it is not yet in the generated matrix.md). Although PostUpdate is an incident communications rule, it checks and cites live ownership facts via LIVE(cf) guards. Thus, an in-flight ownership supersede races with update citations, demonstrating how semantic memory citations create concrete OCC dependencies.
