## Risky decisions

1. **I built to the runbook, not to the chat brief (D-27).** The brief named different files (`audit/{hash,invariants}.py`, `kernel/invariant_probe.py`) and defined K1–K6 differently (K1 = bitemporal, K2 = chain, …). `gate.py` reads SCOPE from the runbook, and contract C1 makes the spec win. Every concern in the brief is still checked, just under the spec's labels: overlap = K5b, chain = K1, lease = K5a, causal = K6. KeyVersion and Outbox state are covered by K4, which compares the whole graph.
2. **Audits stronger than the §12.3 text (D-29).**
   - K6's query cannot see a ghost Rewrite that nothing points to, so K6 also lists Rewrites with no seq.
   - K3 recomputes rule shas, but a forger can compute a valid sha (MU7 does this on purpose). So K3 also requires each Rule to have been written by the Genesis or RegisterRule rewrite at its `registered_seq`.
   - K5c and K5d avoid the S25 shape (a WHERE on an OPTIONAL MATCH).
3. **Another platform quirk (D-30).** An inline map that references a variable bound by an earlier MATCH (`MATCH (w:Rewrite {id: e.rw})`) fails with "Variable not found". WHY-entity therefore uses `WHERE w.id = e.rw`. This is recorded as an observation, not yet a FACTS spike.
4. **The state machine is small: 10 examples × 30 steps.** It does apply claims, completions, expiries, citations, receipts and root causes, and its teardown runs a full replay. Handoff and ResolveIncident rarely apply in random runs. Their transitions are covered by the A06 tests and the scenario.
5. **The stateful test was edited after its RED commit (D-30).** CompleteTask and Handoff can now act as the lease holder, and the run is longer. This makes the test stronger, not weaker, but the edit landed in the feat commit.

## Questions

### Q1. Why does replay pass recorded view keys?

Answer (human): Replay executes historical events sequentially against a clean scratch copy. View keys represent the exact optimistic concurrency control (OCC) read-set footprint evaluated during original rule execution. Passing recorded view keys guarantees that replay reconstructs the exact query scope and conflict boundaries that were present at transaction time, eliminating non-deterministic divergence from ambient or unindexed state.

### Q2. What is in the K4 hash and what is excluded?

Answer (human): - Included: Canonical serialized representation of all committed graph nodes (Entities, Tasks, Incidents, Leases, Rules, Citations) and relationships, sorted deterministically by primary identity, labels, normalized property key/value pairs (HLC timestamps, hashes, strings, integers), and directed relationship topologies with their properties.
- Excluded: Ephemeral execution state, transient replay workspace prefixes (e.g., t:<tenant>:replay:a07-*), active lock tokens, non-deterministic host metadata, outbox in-flight queue transport IDs, and uncommitted staging buffers.

### Q3. Pick one mutation and trace how each listed check detects it.

Answer (human): Mutation: MU7 (Forged Rule node inserted with a validly computed hash).
- K1 (Hash chain): Passes if the attacker correctly computes the sha field.
- K3 (Rule author / provenance audit under D-29): Detects and FAILS immediately. Under D-29, K3 validates the causal creator link and author signature against the event log, exposing the forged rule.
- K4 (Whole-graph canonical replay): FAILS. Replay reconstructs the graph strictly from valid event log transitions where the forged rule event does not exist; the replayed graph hash diverges from the scratch graph.
- K6 (Causal ordering): FAILS if the forged rule lacks a valid transaction sequence linkage (seq) or valid parent rewrite edge.

### Q4. Why compare the citation seq with ts/te instead of pt?

Answer (human): System transaction time (ts/te) and monotonically increasing sequence numbers define the authoritative, immutable bitemporal transaction window in the ledger. Physical time (pt) is subject to NTP skew, clock drift, and worker desynchronization. Comparing citation sequence against ts/te verifies whether a cited fact was unclosed (te = $INF) and valid at the exact transaction sequence, providing mathematical determinism independent of physical wall clocks.

### Q5. What would a K4-only audit miss?

Answer (human): A K4-only audit only verifies terminal state equivalence against a clean replay; it cannot:
1. Pinpoint diagnostic root causes: When a hash diverges, K4 only reports a binary mismatch, whereas K1–K6 pinpoint the exact mutated node, relationship, or rule ID.
2. Detect transient invariant violations: If a mutation violated an intermediate invariant (e.g., a momentary dual lease under I6 or an unauthorized task transition) but subsequent events closed or overwritten the state, K4's final graph hash could match while the execution history broke safety guarantees.
3. Prove audit compliance: It cannot prove that intermediate read guards (G1–G11) were strictly enforced during flight.
