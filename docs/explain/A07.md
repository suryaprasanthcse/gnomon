## Risky decisions

1. **I built to the runbook, not to the chat brief (D-27).** The brief named different files (`audit/{hash,invariants}.py`, `kernel/invariant_probe.py`) and defined K1–K6 differently (K1 = bitemporal, K2 = chain, …). `gate.py` reads SCOPE from the runbook, and contract C1 makes the spec win. Every concern in the brief is still checked, just under the spec's labels: overlap = K5b, chain = K1, lease = K5a, causal = K6. KeyVersion and Outbox state are covered by K4, which compares the whole graph.
2. **Audits stronger than the §12.3 text (D-29).**
   - K6's query cannot see a ghost Rewrite that nothing points to, so K6 also lists Rewrites with no seq.
   - K3 recomputes rule shas, but a forger can compute a valid sha (MU7 does this on purpose). So K3 also requires each Rule to have been written by the Genesis or RegisterRule rewrite at its `registered_seq`.
   - K5c and K5d avoid the S25 shape (a WHERE on an OPTIONAL MATCH).
3. **Another platform quirk (D-30).** An inline map that references a variable bound by an earlier MATCH (`MATCH (w:Rewrite {id: e.rw})`) fails with "Variable not found". WHY-entity therefore uses `WHERE w.id = e.rw`. This is recorded as an observation, not yet a FACTS spike.
4. **The state machine is small: 10 examples × 30 steps.** It does apply claims, completions, expiries, citations, receipts and root causes, and its teardown runs a full replay. Handoff and ResolveIncident rarely apply in random runs. Their transitions are covered by the A06 tests and the scenario.
5. **The stateful test was edited after its RED commit (D-30).** CompleteTask and Handoff can now act as the lease holder, and the run is longer. This makes the test stronger, not weaker, but the edit landed in the feat commit.

## Questions

### Q1. Why does replay pass recorded view keys?

Answer (human): Replay executes historical events sequentially against a clean scratch copy. View keys represent the exact optimistic concurrency control (OCC) read-set footprint evaluated during original rule execution. Passing recorded view keys guarantees that replay reconstructs the exact query scope and conflict boundaries that were present at transaction time, eliminating non-deterministic divergence from ambient or unindexed state.

### Q2. What is in the K4 hash and what is excluded?

Answer (human): - Included: every node and every edge of the tenant graph, the kernel log included (Head, Rewrite, KeyVersion, CAUSED_BY), plus Rules, FactTypes, Outbox rows, IndexEntry/ConstraintEntry catalogue rows and all domain entities and fact edges. A node becomes `N|<key>|<sorted labels>|<JCS(properties)>`, keyed by its logical identity (Entity.uid, Rule.sha, Rewrite.id, KeyVersion.key, FactType.rel, Outbox.pid, `head` for Head). An edge becomes `E|<type>|<key(start)>|<key(end)>|<JCS(properties)>`. The lines are sorted, joined with a newline and SHA-256'd. Editing `Outbox.state` (MU12) is therefore caught by K4.
- Excluded: internal node and edge ids (ordering never depends on them), the physical index and constraint catalogue (that is K8's job, and a test drops and adds an index without changing the hash), and every other graph key, including the scratch replay graph K4 builds and then deletes.

### Q3. Pick one mutation and trace how each listed check detects it.

Answer (human): Mutation: MU7 creates a `Rule` out of band. The listed checks are K3 and K4. The mutation builds a real RuleDef, so its `sha` recomputes correctly from its stored fields, and it gives the node `rw: 'forged'`, `registered_seq: Head.seq` and `active: true`.
- K3: the §12.3 pin query stays silent, because no rewrite uses the forged rule, and the sha recompute stays silent too, because the sha is genuine. What fails it is the provenance check (D-29): the Rule's `rw` must name a Rewrite whose rule is Genesis or RegisterRule and whose seq equals the Rule's `registered_seq`. No Rewrite has id `forged`, so K3 reports `rule_provenance`.
- K4: replay rebuilds the graph only from the recorded rewrites, and none of them created the forged Rule. The replayed graph therefore lacks its `N|<sha>|Rule|…` line, and K4 reports `state_differs` with that line on the live side and nothing on the replay side.
- Not listed, and silent: K1 and K2, because the log is untouched; K5, because no domain facts change; and K6, which only inspects Rewrite nodes and CAUSED_BY edges.

### Q4. Why compare the citation seq with ts/te instead of pt?

Answer (human): System transaction time (ts/te) and monotonically increasing sequence numbers define the authoritative, immutable bitemporal transaction window in the ledger. Physical time (pt) is subject to NTP skew, clock drift, and worker desynchronization. Comparing citation sequence against ts/te verifies whether a cited fact was unclosed (te = $INF) and valid at the exact transaction sequence, providing mathematical determinism independent of physical wall clocks.

### Q5. What would a K4-only audit miss?

Answer (human): K4 trusts the log. It replays the recorded rewrites and compares the result with the live graph, so it can only find state that disagrees with the log. It misses:
1. A log that was forged consistently. If an attacker edits a rewrite and re-chains every later `prev`/`hash` plus Head.hash, replay reproduces the forged history exactly. Only K1 can catch this, by recomputing each hash with `Kernel.chain` from the stored fields and checking the linkage. And if the attacker also recomputes the chain correctly, K1 passes too; that is the limit of an unsigned chain.
2. The rule and kernel pins (K3). K4 replays with the Rule definitions and the Kernel library it finds, so a rule whose fields no longer hash to its sha, or a server running a different Kernel library than Head.kernel_sha pins, can replay "equal" without being noticed. MU6 and the `kernel_sha` test are K3 territory.
3. Log-shape faults that replay never reaches. With K4 alone, a gap or duplicate in seq (K2) or a ghost Rewrite (K6, K2) shows up only as an opaque divergence or difference, not as the broken invariant.
4. Invariants the log itself encodes wrongly. If a rule bug (or a rule registered without guards, MU32) let a rewrite create a second open lease, an overlap, a dead citation or a forward cause, replay reproduces it faithfully and K4 passes. K5a–d and K6 check the invariants I6–I10 directly against the state.

K4 is not a bare yes/no: it reports the first differing canonical line and the properties that differ. But like K1–K6, it inspects only the final state. Violations in the middle of the history that later rewrites repaired are caught only where checks run per step, as the stateful machine does with K5.
