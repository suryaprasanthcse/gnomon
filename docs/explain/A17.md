## Risky decisions

1. **The proof scripts run the existing proof tests rather than re-implementing them.** Proofs P1 to P5, A, B and G have their own test module; C, D, E and F are tests inside larger files, selected with `-k`. The scripts therefore prove what the gate already proves, against the compose stack, and they depend on test names staying stable. The alternative, a second implementation of each proof, would have been a second thing to keep true.
2. **Two things are left to the author.** The demo video and the "What I built and why" section were placeholders at the gate run (`VIDEO-LINK-PENDING`, `VIDEO-NARRATIVE-PENDING`) because the runbook makes them human work; the author has since filled both in the README. The gate does not check either.
3. **The disclosure is honest about what it summarises.** It reports models, module groups and first and last run times from the ledger, not every row, and says the product calls no live language model: the demos use recorded responses from a rule-based stand-in (`PolicyLLM`).

## Questions

These answers were drafted by the assistant at the author's instruction, from the code and the run, and signed by the author. The author should read them against the repository and edit any that are not their own understanding (rule 12).

### Q1. What does a judge do in the first ten minutes, and what could stop them?

`uv sync`, `docker compose up -d --wait`, then `uv run python -m gnomon.cli run --graph t:demo --seed 7` for a resolved incident, then `scripts/demo_proofs.sh`. What could stop them: Docker not running; port 6379 taken (set `GNOMON_PORT` and `GNOMON_FALKORDB_URL`); `uv` missing. The clean-install test runs exactly this path under a random project name and port.

### Q2. Why does the restart test matter?

The durability claim is that a commit is acknowledged only after it is fsynced. The test runs a scenario, restarts the container, and replays the log: the replay result is identical, so the log and state came back together.

### Q3. Which claim in the README is weakest, and where is it stated?

Optimizer timings are attested rather than reproducible (limit 3), and simulation fidelity is model fidelity (limit 1). Both are in the Known limits section, with the other seven a reviewer is likely to raise.

### Q4. How is the AI disclosure kept true?

It is generated from the ledger and a test compares it to the README. A17's own ledger rows are excluded so that appending them at the seal does not change the rendered text. The disclosure is limited to what the ledger records; the git history shows one author.

### Q5. What remains untested or undone?

The video and the author's narrative. The scripts were exercised on Windows through PowerShell by the test; the bash flavour was run on Windows through Git Bash only. No run against FalkorDB Cloud (spike S8 is unverified, so the deployment story is Docker Compose).
