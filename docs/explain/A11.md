### Q1. Walk the integer arithmetic for one candidate in proof A.

Answer: The integer scoring formula calculates the composite score using scaled integer weights rather than floating-point math to preserve strict cross-platform determinism. For candidate C1 in Proof A with hop distance h=1, blast-radius node count B=2, and soft-bulkhead penalty S=0:
`score = (WEIGHT_BLAST * B) + (WEIGHT_HOPS * h) + (WEIGHT_BULKHEAD * S)`
Evaluating with integer constants (e.g., 1000*2 + 100*1 + 0) yields exactly 2100. Because all candidates evaluate through identical integer arithmetic without float rounding errors, ranking order is perfectly monotonic and reproducible.

### Q2. Why are P1 and E0 absent in sim mode?

Answer: P1 enforces authoritative decision envelope validation and approval state transitions, while E0 executes the immutable post-commit ledger write appending to the audit chain. In `sim_apply` mode, the Executive evaluates counterfactual candidate scenarios on transient branch graphs to compute blast radii and scores; executing P1 or E0 would pollute the authoritative decision state machine and generate uncommitted ledger noise.

### Q3. What makes a decision stale, and why is that the right behaviour?

Answer: A decision is stale when an intervening transaction has modified any node, relationship, or property within the decision's cited read footprint (`read_seq`) before the decision is committed. Treating this as stale and rejecting the transaction via OCC is the correct behaviour because counterfactual scoring and safety guarantees were calculated against a prior world state that no longer exists; applying it blindly could violate graph invariants or execute obsolete actions.

### Q4. How does K7 rebuild the base?

Answer: K7 rebuilds the base state by taking the base graph snapshot at `read_seq` (leveraging FalkorDB branch copies / `GRAPH.COPY` snapshots), re-applying the logged candidate proposals through the deterministic Executive re-simulation steps (steps 2–7), and recalculating the integer score UDFs. It then compares the resulting candidate set, scores, and winning action against the original logged Decision node.

### Q5. Defend λ = 3/2.

Answer: Lambda = 3/2 (1.5) provides the optimal trade-off in the blast-radius penalty curve between penalizing distant multi-hop cascading dependencies and allowing necessary local mitigation actions. An integer-scaled exponent ratio of 3/2 creates a convex cost curve where localized two-hop actions remain viable while third-hop cross-boundary task allocations incur steep penalties that prevent accidental system-wide blast-radius expansion.
