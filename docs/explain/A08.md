## Risky decisions

1. **EN-R4 and EN-R10 are tighter than the spec text (D-31).** As written they list tuples whose guard then rejects them (an alert whose service and signature already have an open incident; a deploy that is already the current root cause). The soundness property requires every tuple to apply, so the queries exclude those. R11 and the new counts use `sum(CASE)` over an unfiltered OPTIONAL MATCH (S25).
2. **I corrected one RED test after the RED commit (D-33).** The S23 lint over-reached: it rejected a second aggregate that reads a property, the shape A06's R11 body already runs. It now ignores other aggregates; the check on plain property projections is unchanged. Approved by the human at the G4a checkpoint, with D-31 and D-34.
3. **Defaults the spec leaves open (D-35).** A tuple does not carry an incident id, task ids, a ttl or a confidence, so OpenIncident uses `i-<alert>` with one `ops` task, ttl defaults to 300000 ms and confidence to 50, each overridable only through a small whitelist of params. Tool argument names also differ from §20 where Python forces it: `dependency_path` takes `source` and `target` (D-34).

## Questions

### Q1. Why are algorithm reads advisory?

Answer: Algorithm reads run on the DEP_NOW projection, which shows only current topology, and they record no read: no read_id, no view keys, nothing to cite. A proposal therefore never depends on them, and a stale algorithm result cannot make a bad write apply. Correctness stays with the kernel: the rule's guards and the view keys of the binding reads the proposal does cite.

### Q2. What does id provenance stop?

Answer: It stops an agent from naming an entity id or fid it never read. For an open-parameter rule (PostUpdate, AssertFact.*, RetractFact.*) every id and fid must appear in a read cited from the agent's own session, else the proposal is SCHEMA_REJECTED before composition and nothing reaches the kernel. For enumerated rules the agent gives only a tuple_index and the service builds the parameters, so ids cannot be invented. It is a provenance check against cited reads, not a cryptographic one.

### Q3. Why is read_seq the minimum?

Answer: A proposal may cite several reads taken at different times. Its read_seq is the minimum over them, because the kernel treats any write to a view key after read_seq as a conflict. Using the oldest seq means every cited read is checked against the state it actually saw: a key written after the oldest read makes the proposal REJECTED_STALE, even if a newer read would have been fresh. The maximum would let an old read pass unchecked.

### Q4. How would an agent get a stale proposal applied, and why can't it?

Answer: It would have to cite reads whose view keys omit what it relied on, or give a read_seq newer than its reads. It cannot: the query service computes read_seq (the minimum) and view_keys (the union, phantom keys included, and per-tuple keys for an enumerated tuple) from the reads the session recorded, and the agent never supplies them. The kernel's P0 prelude then rejects with REJECTED_STALE if any view key has a KeyVersion seq above read_seq, as when a rival claims the task between list_actions and propose.

### Q5. Which tool would you cut from a minimal demo, and why?

Answer: I would cut dependency_path. The minimal read-propose-apply loop needs only whoami, list_actions, incident_status, read_entity, facts and propose. The six algorithm tools (neighborhood, rank_critical, brokers, failure_domains, communities, dependency_path) are advisory and nothing in a proposal depends on them. dependency_path is the most specialised of them and neighborhood already covers a service's reach, so it adds least to a demo.
