## Risky decisions

1. **EN-R4 and EN-R10 are tighter than the spec text (D-31).** As written they list tuples whose guard then rejects them (an alert whose service and signature already have an open incident; a deploy that is already the current root cause). The soundness property requires every tuple to apply, so the queries exclude those. R11 and the new counts use `sum(CASE)` over an unfiltered OPTIONAL MATCH (S25).
2. **I corrected one RED test after the RED commit (D-33).** The S23 lint over-reached: it rejected a second aggregate that reads a property, the shape A06's R11 body already runs. It now ignores other aggregates; the check on plain property projections is unchanged. Approved by the human at the G4a checkpoint, with D-31 and D-34.
3. **Defaults the spec leaves open (D-35).** A tuple does not carry an incident id, task ids, a ttl or a confidence, so OpenIncident uses `i-<alert>` with one `ops` task, ttl defaults to 300000 ms and confidence to 50, each overridable only through a small whitelist of params. Tool argument names also differ from §20 where Python forces it: `dependency_path` takes `source` and `target` (D-34).

## Questions

### Q1. Why are algorithm reads advisory?

Answer: Algorithm reads (e.g., shortest path, topological dependency paths, connected components) run across potentially changing graph topologies to assist agents in planning and proposal generation. Because graph mutations occur concurrently, an algorithm read reflects a point-in-time snapshot and holds no optimistic concurrency locks. The actual kernel write path evaluates strict antecedent guards independently at transaction time, meaning algorithm reads guide decisions but cannot guarantee that path topologies remain unchanged.

### Q2. What does id provenance stop?

Answer: Id provenance stops ID injection and spoofing attacks. By cryptographically binding and verifying the lineage of generated or referenced entity/node IDs back to an authoritative genesis transaction, rule execution, or caller identity, it prevents malicious or rogue agents from manufacturing arbitrary IDs to bypass ownership checks or overwrite unassociated subgraphs.

### Q3. Why is read_seq the minimum?

Answer: `read_seq` represents the highest transaction sequence observed by the client when it read the state used to construct a proposal. Requiring `read_seq` as the lower bound in optimistic concurrency control (OCC) ensures that the kernel rejects any proposal attempting to evaluate against an older, stale ledger baseline, enforcing that mutations only apply if no intervening conflicting writes touched the read footprint.

### Q4. How would an agent get a stale proposal applied, and why can't it?

Answer: An agent could get a stale proposal applied only if the transaction engine lacked OCC view-key conflict detection and allowed blind writes. It cannot succeed in Gnomon because every proposal carries the read-set's view keys and `read_seq`. When the proposal enters the write pipeline, the kernel checks whether any committed transaction between `read_seq` and current head touched any key in the proposal's view-key footprint (via KeyVersion checks or guard probes). If any overlap exists, the transaction fails OCC validation with REJECTED_STALE_VIEW.

### Q5. Which tool would you cut from a minimal demo, and why?

Answer: `dependency_path` (or large-radius blast-radius inspection). For a core deterministic ledger demo, basic point reads (`get_entity`, `get_task`, `list_incidents`) and direct enablement tuples (`get_enabled_actions`) are sufficient to demonstrate the complete read-propose-apply loop and guard enforcement. Multi-hop path algorithms are analytical convenience tools rather than critical substrate primitives.
