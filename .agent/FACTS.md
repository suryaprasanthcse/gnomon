# PLATFORM FACTS (A01, gate G0)

Observed on the pinned image (graph module 60002, built 2026-10-08) on 2026-10-15. Each line is checked
by its spike test in tests/spikes/: a different verdict on a future image fails the test. Later modules

## Facts (master §23.1)

F1: PASS → GRAPH.COPY is a snapshot: writes to the source after the copy are not visible in the destination; the copy carries indexes and constraints (operational and enforced), which patch P3 relies on; copying onto an existing key fails ("destination key already exists")
F2: PASS → FOREACH accepts CREATE, MERGE, SET, REMOVE, DELETE and nested FOREACH, and sees outer variables
F3: FAIL → CREATE INDEX FOR ()-[f:R]-() ON (f.p) works and EXPLAIN shows Edge By Index Scan, but DROP INDEX ON :R(p) fails for relationship indexes ("Unable to drop index on :R(p): no such index"). DROP INDEX FOR ()-[f:R]-() ON (f.p) drops it; DROP INDEX ON :L(p) still works for node indexes; fallback: the optimizer and reconciler use the FOR-pattern drop for relationship indexes (DECISIONS D-6)
F4: PASS → GRAPH.CONSTRAINT CREATE replies PENDING; db.constraints() (type, label, properties, entitytype, status) reaches OPERATIONAL; creating a constraint without its supporting index fails with "missing supporting exact-match index"
F5: PASS → GRAPH.PROFILE lines follow master §16.3: 4-space indent per level, "Op[ | argument] | Records produced: <int>, Execution time: <float> ms"
F6: PASS → algo.pageRank(label, relType); algo.betweenness({nodeLabels, relationshipTypes, samplingSize, samplingSeed}); algo.WCC({…}) YIELD node, componentId; algo.labelPropagation({…, maxIterations}) YIELD node, communityId; algo.bfs(node, depth, relType) YIELD nodes, edges; algo.SPpaths({…}) YIELD path, pathWeight, pathCost; algo.maxFlow({sourceNodes, targetNodes, capacityProperty, relationshipTypes}) YIELD nodes, edges, edgeFlows, maxFlow
F7: PASS → falkor.register (plus falkor.log); node.getNeighbors({direction, types, returnType}); graph.getNodeById(id) (null when absent); graph.traverse([nodes], {direction, types}) returns one list of direct neighbours per start node (a `distance` option is ignored); graph.iterateNodes(label) and graph.iterateEdges(type) take one string. Changes a UDF makes to node objects are never written to the graph

## Hazards observed after A01 (not §23.2 spikes; written as `- S<n> (<module>):` so the A01 registry does not parse them)

- S23 (A02, FAIL → server panic): a RETURN that projects a property access after an aggregate, e.g. `MATCH (h:Head) OPTIONAL MATCH (r:Rewrite) RETURN h.seq, count(r), h.z`, kills the server with `FalkorDB panic: panicked at src/reply.rs:655:58: called Option::unwrap() on a None value` in `falkordb::reply::reply_compact` (the compact reply the Python client requests). Observed on the pinned image whether or not the attribute exists, with no UDF and no thrown error. The same columns with the aggregate last (`RETURN h.x, count(r)`), or without an aggregate, work. Found while A02 checked a UDF-throw rollback: the rollback itself was correct (S4 holds). Fallback: never place a property projection after an aggregate in a RETURN or WITH; put aggregates last or read them in a separate query (DECISIONS D-8). There is no spike test: reproducing it would take down the shared test container

- S24 (A05, FAIL → server panic): a write slow enough to enter the slow log has its query text truncated at byte 2048 (`src/slow_log.rs:49`); when that byte falls inside a multi-byte UTF-8 character the server aborts (`end byte index 2048 is not a char boundary`, then SIGABRT). Reproduced on the pinned image with `UNWIND range(1, 300000) AS i CREATE (:N {v: i})` preceded by a comment whose `─` straddles byte 2048: 4 of 6 offsets crash, the ASCII version never does. Parameters are not affected: a non-ASCII parameter value straddling byte 2048 of the CYPHER header crashed 0 of 12 times. Seen first when the A05 gate's parallel load made a composed query (segments and bodies carry `─`/`·`/`§` in comments) slow. `\uXXXX` escapes are decoded in string literals; surrogate-pair escapes are rejected ("Invalid unicode code point"). Fallback: the kernel service sends composed queries with comments stripped, i.e. ASCII text (DECISIONS D-20). No spike test: reproducing it kills the shared container

- S25 (A06, FAIL → wrong result): after `MATCH (i:Incident {id: $x})-[:AFFECTS]->(s:Service)`, an `OPTIONAL MATCH (t:Task)-[:PART_OF]->(i)` and an aggregating `WITH`, the clause `OPTIONAL MATCH (i)-[rc:ROOT_CAUSE]->() WHERE rc.te = $INF` finds nothing although the edge exists and `rc.te = $INF` evaluates true: EXPLAIN shows the Filter placed under the optional Conditional Traverse, on its Argument, before `rc` is bound. The same clause works without the AFFECTS hop, without the aggregation, or with the filter moved after the match (`WITH i, rc WHERE …`, or `sum(CASE WHEN … THEN 1 ELSE 0 END)`). Other optional-with-WHERE shapes in the core rules (ClaimTask's lease check, OpenIncident's open duplicate, ProposeCause's current cause and cites) were checked by their guard tests and behave correctly. Fallback: ResolveIncident counts current root causes with sum(CASE …) (DECISIONS D-25); a new body that filters an OPTIONAL MATCH after an aggregation must be covered by a guard test
